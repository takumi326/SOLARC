■0 カード定義

台帳はカードごとに独立して作る。アプリが注入するカード定義は次のとおり。

  card_id      : アプリ側で使う識別子（JSON の card_id にそのまま書く）
  card_name    : 表示名
  cycle        : 締め日 / 支払日
  source       : 利用通知の取得元（vpass / paypay_flash）
  vpass_label  : VPass本文の「〜についてカードの利用内容をお知らせします」に現れる文字列
  flash_subject: PayPay利用速報の件名
  paypal_funding: PayPal領収書の支払元表記（例 Mastercard-8225）。未連携は null

現行の定義:

{{CARDS}}

実行対象の要約:
{{CARD_WORKFLOW}}

対象期間は {{TARGET_MONTH}}（カードを利用した月）。

重要: 上記すべての card_id を1回の実行で処理する。
カードごとにメール取得・分類は独立して行うが、最終出力は card_id が混在した JSON 配列1本にまとめる。
カードごとに JSON を分けたり、複数回に分けて出力してはならない。


■1 前提

・支出はカードに乗った取引を1行として台帳にする。取得元は次の3系統。
    A) VPass の利用通知メール      … source=vpass のカードの直接決済
    B) PayPayカードの利用速報メール … source=paypay_flash のカードの直接決済
    C) PayPal の領収書メール        … PayPal 経由（どのカードに乗るかは領収書本文で判定）

  PayPal 経由の決済は A にも B にも通知が出ない。よって A/B と C は重複しない。

・各サービス（Google Play・出前館・Uber Eats・Nintendo・Amazon・Yahoo!ショッピング等）の
  メールは台帳の行にしない。中身を埋めるための補助資料として使う。

・重要
  A も B も「承認照会に基づく通知」であり、請求の確定ではない。
  したがって次が起こりうる。台帳と請求額の不一致は必ずしも取りこぼしではない。
    ・与信額と確定額が違う（ガソリン、ホテル、レンタカー等）
    ・キャンセル・返品が発生しても通知は飛ばない
    ・売上到着が遅れて翌月以降の請求に回る


■2 鉄則（これを守らないと静かに金額が欠ける）

search_threads が返してきたメッセージ一覧を集計に使ってはならない。
同じ件名のメールが連続すると1スレッドに束ねられ、search_threads は
その一部しか返さないことがある。

必ず次の手順を踏むこと。
  1. search_threads はスレッド id を集めるためだけに使う。
  2. 得られた全スレッドに対して get_thread を実行する。
  3. get_thread が返したメッセージ全件を台帳の対象とする。

件数チェックだけでは検知できない。最後の突合まで必ず行うこと。

messageFormat の指定
  VPass  : MINIMAL でよい。snippet に日時・加盟店名・金額がすべて入る。
  PayPay : MINIMAL でよい。ただし snippet は金額のカンマが落ちる（20000円）。
           plaintextBody はカンマが残る（20,000円）。両方を許容する正規表現にすること。
  PayPal : FULL_CONTENT が必要。snippet には支払元カードと商品名が入らない。
           ただし htmlBody は非常に大きいので、必要フィールドだけ抜いて捨てること。
           例外: paypal_funding が非nullのカードが1枚しかない場合は MINIMAL で済ませてよい。
           ただしこの近道には盲点がある。MINIMALでは支払元カードが読めないため、
           PayPal側で支払元カードを変更しても検知できず、旧カードに付け続けてしまう。
           対策として、対象月のPayPal領収書のうち任意の1通だけは必ず FULL_CONTENT で取得し、
           支払元表記がカード定義の paypal_funding と一致することを確認する。
           一致しなければ、その月の全PayPal行を FULL_CONTENT で取り直すこと。
           確認結果は検算欄に「PayPal支払元チェック: Mastercard-8225 / OK」の形で必ず出す。


■3 手順1 台帳の作成


[1-A] VPass（source=vpass のカード）

検索条件
  from:statement@vpass.ne.jp subject:"ご利用のお知らせ"
  after:{{対象月初日の前日 YYYY/MM/DD}} before:{{対象月末日の翌々日 YYYY/MM/DD}}

本文の形
  {カード名}についてカードの利用内容をお知らせします。
  ご利用日時：2026/08/10 00:32
  {加盟店名}（{区分}） {金額}円

ルール
1. 鉄則どおりスレッド id を集めてから get_thread で全メッセージを取る。
2. カード判定は「{カード名}についてカードの利用内容をお知らせします」から行い、
   カード定義の vpass_label と突き合わせる。全角英数を含むので正規化してから比較すること
   （例: Ａｍａｚｏｎマスター）。どの vpass_label にも一致しないカード名が出たら、
   行は残したうえで card_id = "unknown" とし、検算欄の先頭に警告として出す。
3. 日付は必ず本文の「ご利用日時」を使う。メールヘッダの date は UTC なので1日ずれる。
4. 件名が「お支払い金額のお知らせ」等のものは除外する。
5. 区分が「買物」以外の行（返品・キャンセル・キャッシング等）は 3-D の扱いにする。
6. 円建てでない金額は 3-C の扱いにする。
7. 「ご利用日時」が対象月内のものだけ残す。

行の項目: card_id / ご利用日時 / 加盟店名 / 区分 / 金額 / message_id / 経路=card


[1-B] PayPayカード（source=paypay_flash のカード）

検索条件
  from:paypaycard-info@mail.paypay-card.co.jp subject:利用速報
  after:{{対象月初日の前日 YYYY/MM/DD}} before:{{対象月末日の翌々日 YYYY/MM/DD}}

注意: 送信元アドレスは販促メールと同一である。件名での絞り込みを外してはならない。

本文（plaintextBody）の形
  PayPayカード（JCB）利用速報

  {加盟店名}
  2026年8月3日 21:04
  20,000円

ルール
1. 鉄則どおり get_thread で全メッセージを取る。
2. カード判定は件名をカード定義の flash_subject と突き合わせる。
3. 日付は本文の「YYYY年M月D日 HH:MM」を使う（JST）。ヘッダの date は使わない。
4. 金額はカンマあり／なしの両方を許容する。
5. 本文の日付が対象月内のものだけ残す。
6. PayPay残高へのチャージが速報に出た場合は資金移動なので 3-E の扱いにする。

行の項目: card_id / 利用日時 / 加盟店名 / 金額 / message_id / 経路=card


[1-C] PayPal

検索条件
  from:service-jp@paypal.com
  after:{{対象月初日の前日 YYYY/MM/DD}} before:{{対象月末日の翌々日 YYYY/MM/DD}}

領収書から取るフィールド
  取引ID / 取引日 / マーチャント / 説明 / 合計 / 支払元

ルール
1. 鉄則どおり get_thread で全メッセージを取る。ここが一番束ねられやすい。
2. 件名が「〜様への支払いの領収書」のものを対象とする。
3. カード判定は支払元表記をカード定義の paypal_funding と突き合わせる。
   一致するものがなければ card_id = "unknown" とし、検算欄に警告を出す。
4. 日付は本文の「取引日」を使う。対象月内のみ残す。
5. マーチャント名も説明も末尾が「...」で切られていることがある。前方一致で扱うこと。
6. 「支払いを承認しました」の扱い
   a. 同じ取引の領収書が期間内にあれば領収書を採用し承認は捨てる（取引IDで判定）。
   b. 領収書が無い承認は台帳に載せ、memo 先頭に「[承認のみ]」。行を落としてはならない。
   c. b の行は検算欄の「承認のみリスト」に取引IDとともに列挙する。


■4 手順2 分類

台帳の各行について 2-1 から順に判定し、最初に当たった時点で確定する。
判定は card_id ごとに独立して行う。


[2-1] 定期課金（確定済み辞書）

カード直接の行は、加盟店名ではなく「金額 かつ 日付ウィンドウ」で判定する。

  smcc_amazon / VPass経由
    800円   毎月1日ごろ  → Note（グリーンさん）
    9,075円 毎月13日ごろ → エニタイム
    748円   毎月1日ごろ  → ドスパラ PC保証（この行だけ前後10日）

  smcc_amazon / PayPal経由
    290円   毎月15日ごろ → Google Storage
    650円   毎月3日ごろ  → LYPプレミアム スタンダードプラン
    1,280円 毎月23日ごろ → YouTube Premium

  paypay_jcb
    （現時点で定期課金なし）

判定条件
  ・カード直接: 金額の完全一致 かつ 日付が該当日の前後3日以内（748円のみ前後10日）
  ・PayPal: まず領収書の「説明」を見る。取れない場合のみ金額＋日付ウィンドウにフォールバック。

一致したら memo = サービス名、minor_category_id は下記一覧のサブスク相当を選ぶ。


[2-2] 加盟店名で判定できるもの

  次の加盟店ルールに一致したら、対応する minor_category_id を選び、memo = 加盟店名。

{{MERCHANT_RULES}}

  注意: 加盟店名が「ＡＭＡＺＯＮ．ＣＯ．ＪＰ」でも Amazon の買い物とは限らない。
  AMAZON 表記の行は 2-3 の突合も必ず行うこと。


[2-3] 中身の特定（補助メールとの突合）

  対象
    ・加盟店名が「Mastercard加盟店」「Visa加盟店」「AMAZON.CO.JP」の行
    ・PayPal経由で、領収書の「説明」から中身が特定できなかった行のみ

  補助メールの検索先（いずれも鉄則どおり get_thread で全件）
    Google Play / 出前館 / Uber Eats / Nintendo / Amazon / Yahoo!ショッピング

  検索範囲は各行の日付の −2日 から +3日。Amazon のみ −2日 から +10日。
  金額は完全一致。近い金額でのマッチは禁止。一度使った補助メールは二度使わない。


[2-4] どれにも当たらないもの

  memo = 「要確認: <加盟店名 または マーチャント名>」とし、
  minor_category_id は下記一覧の未分類相当を選ぶ。
  行を削除してはならない。


■5 例外行の扱い

[3-C] 外貨建て
  ・円換算額が確定している → 台帳に載せる。memo に原通貨額を併記。
  ・円換算額が未確定 → 保留リスト。検算欄に原通貨額と概算円換算額を出す。

[3-D] 返金・キャンセル・返品
  amount にマイナス値を許容する。memo 先頭に「[返金]」。

[3-E] 資金移動（消費ではないもの）
  スターバックスeGift / 商品券 / PayPay残高チャージ等。
  小カテゴリ一覧に資金移動相当があればそこに寄せる。無ければ未分類＋検算欄「資金移動候補」。


■6 手順3 出力

JSON 配列のみを出力する。説明文、バッククォート、コメントは禁止。

キー
  date              YYYY-MM-DD。利用日
  month             YYYY-MM。date の月と必ず一致
  card_id           カード定義の card_id。不明は "unknown"
  minor_category_id 数値。下記一覧のいずれか
  amount            数値。円。返金はマイナス
  memo              文字列
  source_id         PayPal行は取引ID、それ以外は message id

全カード・全行を1配列にまとめる。card_id の混在は必須。

利用可能な小カテゴリ（支出）
{{CATALOG}}

出力例
[
  {"date":"2026-07-20","month":"2026-07","card_id":"smcc_amazon","minor_category_id":{{EXAMPLE_MINOR_ID}},"amount":4500,"memo":"アークナイツ","source_id":"18c5f2a3b4d5e6f7"},
  {"date":"2026-08-03","month":"2026-08","card_id":"paypay_jcb","minor_category_id":{{EXAMPLE_MINOR_ID}},"amount":20000,"memo":"Yahoo!ショッピング","source_id":"19fc78a82c123bce"}
]


■7 手順4 検算

JSON 配列の後に --- を1行だけ入れ、その下に次を出す。アプリは --- より前だけをパースする。

まずカードごとに出す。
  [card_id] card_name
    ・利用通知（VPass または PayPay速報）の件数と合計
    ・PayPal経由の件数と合計
    ・カード小計
    ・「要確認」 / 「[承認のみ]」 / 「[返金]」 / 資金移動候補

続いて全体。
  ・総合計（全カード）
  ・card_id = "unknown" の件数と内訳
  ・保留リスト（外貨建てなど）

一次検算（毎回）: get_thread 全実行・件数の整合。
二次照合（明細確定後）: カードごとに明細↔台帳を1対1。合計一致は合格条件にしない。
