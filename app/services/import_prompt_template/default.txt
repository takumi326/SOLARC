■前提

・支出はすべて {{PAYMENT_METHOD_NAME}}（三井住友カード / 月末締め・翌月26日払い）で払っている。
・カードに乗った取引を1行として台帳を作る。台帳のソースは次の2系統だけ。
    A) VPass の利用通知メール … カード直接の決済
    B) PayPal の領収書メール   … PayPal 経由の決済
  PayPal 経由の決済は明細には「PayPal決済」として載るが、VPass の利用通知は飛ばない。
  よって A と B は重複しない。両方を足したものがカード請求額になる。
・Google Play・出前館・Uber Eats・Nintendo・Amazon などの各サービスのメールは、
  台帳の行にはしない。中身（品名・店名）を埋めるための補助資料として使う。
・対象期間は {{month}}（例: 2026-07。カードを利用した月）。


■鉄則（これを守らないと静かに金額が欠ける）

search_threads が返してきたメッセージ一覧を集計に使ってはならない。
同じ件名のメールが連続すると1スレッドに束ねられ、search_threads は
その一部しか返さないことがある。

必ず次の手順を踏むこと。
  1. search_threads はスレッド id を集めるためだけに使う。
  2. 得られた全スレッドに対して get_thread（messageFormat: MINIMAL）を実行する。
  3. get_thread が返したメッセージ全件を台帳の対象とする。

ソシャゲ課金のように同じ件名が短時間に連射されるケースでは、これを省くと
数件〜十数件が丸ごと消える。件数チェックだけでは検知できないので、
最後の合計突合まで必ず行うこと。


■手順1-A 台帳の作成（VPass = カード直接）

検索条件
  from:statement@vpass.ne.jp subject:"ご利用のお知らせ"
  after:{{対象月初日の前日 YYYY/MM/DD}} before:{{対象月末日の翌々日 YYYY/MM/DD}}

ルール
1. 上の鉄則どおり、スレッド id を集めてから get_thread で全メッセージを取る。
2. snippet に「ご利用日時 / 加盟店名 / 金額」が入っている。原則これで足りる。
3. 日付は必ず本文の「ご利用日時」を使う。メールヘッダの date は UTC なので1日ずれる。
   例: ご利用日時 2026/08/02 07:46 → ヘッダは 2026-08-01T22:47Z。
4. 件名が「お支払い金額のお知らせ」等のものは除外する。
5. 円建てでない金額（例: 1.00 USD）は台帳に載せず、末尾の保留リストに回す。
6. 「ご利用日時」が対象月内のものだけ残す。

行の項目: ご利用日時 / 加盟店名 / 金額 / message_id / 経路=カード


■手順1-B 台帳の作成（PayPal）

検索条件
  from:service-jp@paypal.com
  after:{{対象月初日の前日 YYYY/MM/DD}} before:{{対象月末日の翌々日 YYYY/MM/DD}}

ルール
1. 鉄則どおり get_thread で全メッセージを取る。ここが一番束ねられやすい。
2. 件名が「〜様への支払いの領収書」のものを対象とする。
3. 「支払いを承認しました」は与信段階の通知。同じ取引で後から領収書が来る場合は
   領収書を優先し、承認だけのものは取引IDで重複を確認したうえで1件として扱う。
4. 日付は本文の「取引日」を使う。
5. 「取引日」が対象月内のものだけ残す。

行の項目: 取引日 / マーチャント名 / 金額 / 取引ID / message_id / 経路=PayPal


■手順2 分類

台帳の各行について 2-1 から順に判定し、最初に当たった時点で確定する。

[2-1] 定期課金（確定済み辞書。加盟店メールを引く必要はない）

  カード直接
    加盟店名「ノート」        800円  毎月1日ごろ   → Note（グリーンさん）
    加盟店名「エーエフトラノモン」9,075円 毎月13日ごろ → エニタイム
    加盟店名「ドスパラ」       748円  毎月1日ごろ   → ドスパラ PC保証

  PayPal
    290円   毎月15日ごろ → Google Storage
    1,280円 毎月23日ごろ → YouTube Premium

  PayPal 側は明細上どちらも「PayPal決済」で名前が潰れるため、金額だけで判定すると
  同額のソシャゲ課金と誤爆する。必ず「金額 かつ 日付が該当日の前後3日以内」を条件にすること。
  条件から外れたものは定期課金と見なさず、2-3 に流す。

  一致したら memo = サービス名、minor_category_id は下記一覧のサブスク相当を選ぶ。

[2-2] 加盟店名で判定できるもの

  {{MERCHANT_RULES}} に一致したら、対応する minor_category_id、memo = 加盟店名。

  注意: 加盟店名が「ＡＭＡＺＯＮ．ＣＯ．ＪＰ」でも Amazon の買い物とは限らない。
  出前館などを Amazon Pay で払うとこの表記になる（明細上は「AmazonPay提携サイト」）。
  AMAZON 表記の行は 2-3 の突合も必ず行うこと。

[2-3] 中身の特定（補助メールとの突合）

  加盟店名が「Mastercard加盟店」「Visa加盟店」「AMAZON.CO.JP」の行、および
  PayPal 経由の全行は、金額と日付で補助メールを突合して中身を特定する。

  補助メールの検索先（いずれも鉄則どおり get_thread で全件取ること）
    Google Play … subject:"Google Play のご注文明細"
    出前館       … from:demae-can.com OR from:demae-can.co.jp
    Uber Eats    … from:uber.com
    Nintendo     … from:accounts.nintendo.com
    Amazon       … from:amazon.co.jp

  検索範囲は各行の日付の −2日 から +3日。
  Amazon は発送時に課金されるため、注文日と台帳の日付が数日ずれる。

  突合ルール
  ・金額は完全一致であること。近い金額でのマッチは禁止。
  ・候補が複数あれば日時が最も近いものを選ぶ。
  ・一度使った補助メールは二度使わない。同額の連続課金があるため 1対1 の対応を守る。
  ・Google Play で支払い方法が「Google Play における残高」のみの注文はカードに乗らないので
    候補から除外する。残高とカードの分割払いの場合は、カード側の金額だけが一致するはず。
  ・Google Play の定期購入（GPY. / GPAS. / SOP. 番号、本文に「定期購入を継続し」）に
    当たったら 2-1 と同じサブスク扱いにする。
  ・突合できたら memo にゲーム名・アイテム名・店名を入れる。

[2-4] どれにも当たらないもの

  memo = 「要確認: <加盟店名 または マーチャント名>」とし、
  minor_category_id は下記一覧の未分類相当を選ぶ。
  行を削除してはならない。削除するとカード請求額と一致しなくなる。


■手順3 出力

JSON 配列のみを出力する。説明文、バッククォート、コメントは禁止。

キー
  date              YYYY-MM-DD 形式。VPass行は「ご利用日時」、PayPal行は「取引日」
  month             YYYY-MM 形式の利用月。date の月と必ず一致させる
  minor_category_id 数値。下記一覧の id のいずれか
  amount            数値。円、0以上。支出はプラスの数で
  memo              文字列
  source_id         PayPal行は取引ID、VPass行は message id

利用可能な小カテゴリ（支出）
{{CATALOG}}

出力例
[{"date":"2026-07-20","month":"2026-07","minor_category_id":{{EXAMPLE_MINOR_ID}},"amount":4500,"memo":"アークナイツ：エンドフィールド 協約起源パック","source_id":"2WA22952EX114591B"}]


■手順4 検算

JSON 配列の後に --- を1行だけ入れ、その下に次を出す。アプリ側は --- より前だけをパースする。

・VPass行の件数と合計
・PayPal行の件数と合計
・総合計
・「要確認」の件数と内訳
・保留リスト（外貨建てなど対象外にした行）

総合計は Vpass アプリの「翌月◯日お支払い分」の金額と一致するはずである。
一致しない場合、まず疑うのは get_thread の取りこぼし。鉄則の手順を踏んだか確認すること。

なお明細に載る日付はカード会社への売上到着日であり、利用日とは数日ずれる。
月末月初の取引は、この JSON の月と明細上の月が食い違うことがある。
金額の合計が合っていれば正常。
